# Rétrospective de l'Epic 1 — Fondation & Infrastructure

**Date :** 2026-08-23
**Statut :** terminée
**Participants :** boss (Project Lead), Amelia (Developer), John (Product Manager), Winston (Architect), Sally (UX Designer), Dana (QA Engineer)

## Résumé de l'epic

L'Epic 1 a livré les cinq stories prévues :

1. Scaffolding du projet Android
2. Schéma de base de données Room
3. Interface `GameEngine` et implémentation Papayoo
4. Système de design sombre et tokens
5. Graphe de navigation et reprise automatique

Les cinq stories sont au statut `done`. Les critères d'acceptation sont documentés comme validés. Les validations disponibles comprennent les tests JVM, la génération KSP, l'assemblage debug et une vérification manuelle sur émulateur du démarrage avec ou sans Partie en cours.

Aucune métrique de couverture, de vélocité ou d'incident de production n'est disponible. L'application reste en développement local.

## Ce qui a bien fonctionné

### Boucle implémentation puis revue

Le principal succès identifié par le Project Lead est l'enchaînement systématique du code puis de la revue. Chaque revue a apporté une amélioration concrète avant la clôture de la story.

Exemples :

- Story 1.2 : renforcement de l'unicité des manches, de l'atomicité Room et de l'intégrité référentielle.
- Story 1.4 : amélioration de la traçabilité des validations, notamment pour les fichiers non suivis.
- Story 1.5 : détection et correction d'une course entre deux tentatives de reprise.

### Architecture cohérente

La séparation `UI → Domain ← Data` a été préservée. Les patterns établis sont réutilisables pour les prochains epics :

- use cases dépendant des contrats du domaine ;
- repositories comme frontière de persistance ;
- `StateFlow` et états fermés pour l'orchestration UI ;
- routes typées avec Navigation Compose ;
- multibinding Hilt pour les moteurs de jeu ;
- faux objets locaux dans les tests JVM.

### Validation adaptée au risque

Les stories ont utilisé des contrôles ciblés avant les validations plus larges : tests JVM, `kspDebugKotlin`, `assembleDebug`, contrôles d'architecture et vérifications manuelles lorsque nécessaires.

## Difficultés rencontrées

### Compatibilité de la stack

La principale friction a été la compatibilité entre Kotlin, AGP, KSP, Hilt, Compose et le JDK pendant la story 1.1. Les versions présentes dans les anciens documents de planification ne reflétaient plus toutes les contraintes réelles de l'outillage.

La résolution a consisté à vérifier les versions opérationnelles, à verrouiller les sources de vérité dans les fichiers Gradle et à consigner JDK 17 et les versions retenues dans le contexte projet.

### Preuves de complétude

Certaines tâches ont initialement été déclarées réussies avant que toutes les preuves soient disponibles. Les stories suivantes ont amélioré ce point grâce au Dev Agent Record, aux validations explicites et au contrôle des fichiers suivis comme non suivis.

## Enseignements

1. Une story n'est réellement terminée qu'après une revue indépendante, le traitement de ses findings et une nouvelle validation ciblée.
2. Toute modification de stack doit commencer par un préflight avant le travail fonctionnel.
3. Les invariants métier et techniques doivent être vérifiés au niveau le plus bas capable de les réfuter.
4. Les fichiers Gradle sont la source de vérité des versions ; les documents de contexte doivent être actualisés lorsqu'elles changent.

## Actions validées

### 1. Préflight de stack

- **Propriétaire :** Developer
- **Déclencheur :** toute story modifiant versions, plugins, JDK ou génération KSP
- **Action :** vérifier la compatibilité, le JDK sélectionné, la résolution Gradle et un build minimal avant l'implémentation fonctionnelle
- **Critère de réussite :** préflight documenté et vert dans le dossier de story

### 2. Maintenir la boucle code → revue → revalidation

- **Propriétaire :** Équipe de développement
- **Déclencheur :** chaque story
- **Action :** exécuter une revue indépendante, corriger ou différer explicitement les findings, puis relancer le contrôle ciblé pertinent
- **Critère de réussite :** aucun finding non traité lors du passage de la story à `done`
